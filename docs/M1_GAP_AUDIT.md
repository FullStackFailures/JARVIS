# M1 gap audit: architecture -> implementation

Audit date 2026-10-04. Baseline: `JARVIS_ARCHITECTURE.md` (section "FIRST IMPLEMENTATION MILESTONE" and its acceptance criteria).
Environment of record: Ubuntu 24.04 container, Python 3.13.15, headless, root, no systemd as PID 1, no PyPI (no ruff/mypy/pytest/import-linter), **no Windows**.

## 0. Verdict on the earlier claim

"Milestone 1 is finished" was **wrong and premature**. At the time of the claim the headline deliverable, `jarvis` CLI -> `jarvisd` over local IPC,
did not exist (only a pydantic schema file). Also missing: 7 of the 14 mandated tools (`system.service_status`, `net.port_owner`, `process.list`,
`fs.search`, `fs.read`, `apps.status`, `notes.write`), the port/service/SSH scenarios, the compat matrix, import-linter config, `ToolRegistry.query`,
an explicit fail-closed path for a crashing policy engine, and any `windows_only` test. The suite was green because it only tested what existed.
The audit below is the status **after** closure work in this session; the "Initial" column records what was true before.

Status vocabulary (exactly one per row):
`IV` = IMPLEMENTED + VERIFIED (executed here, on the platform named) - `INV` = IMPLEMENTED + NOT VERIFIED - `PART` = PARTIALLY IMPLEMENTED - `MISS` = MISSING - `BLOCKED` = BLOCKED BY ENVIRONMENT.
A row is `IV` only for the platform in the Evidence column. Windows is never inferred from Linux.

## 2. Order deviations

| Deviation | Assessment |
|---|---|
| Gateway + Ollama/remote adapters built in M1 (architecture: M2) | **Harmless/beneficial**: the native path never calls them; they are isolated behind `ModelGateway` and layer-tested. Cost: tested only against stub HTTP servers, never a real Ollama/API: marked INV. Do not extend before M2 evidence. |
| Executor/policy/audit built before OSAL ops and tools | **Beneficial**: forced every tool through the boundary from the start. |
| Daemon/IPC built last, after tools and brain | **Needed correction (done)**: it is M1's headline deliverable and also the transport the CLI approval flow depends on. Building it last meant ~half of the scenarios were first proven in-process only; this session re-proved them through the daemon. |
| Tool granularity (`system.memory`/`system.disk` instead of one `system.cpu_mem_disk`) | **Harmless**: smaller blast radius per policy decision, enables the parallel scenario. Documented D-03. |
| Tests on stdlib unittest, not pytest | **Environment-forced**; CI uses the same runner so local == CI. Revisit if pytest becomes available. |
| Windows adapter written without a Windows machine | **Risk accepted, labelled INV everywhere**; verification procedure in `docs/WINDOWS_VERIFICATION.md`. |
